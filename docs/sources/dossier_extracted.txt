Project thesis
GridAid is a browser-based resilience planning platform that combines road-network algorithms, facility-
location optimization, machine learning, Monte Carlo simulation, and disruption analysis to identify
limited emergency-resource configurations that remain effective when conditions change.
The project is built around a planning problem rather than a dispatch problem. A community may know that it has
ten emergency kits, several temporary response teams, a set of public facilities, or a limited number of other critical
resources. The obvious question is where those resources should be placed. The more diﬀicult question is whether that
placement still performs well when a road closes, winter weather slows travel, one resource becomes unavailable, or
demand temporarily shifts.
GridAid models those conditions before an incident occurs.
The competition prototype is aplanning and simulation tool , not a 911 dispatch system, medical application, or
promise about real emergency outcomes. It uses public, synthetic, and documented data; exposes the assumptions
behind its results; and validates its algorithms independently.
The project has five technical pillars:
1. Geospatial computing: build a real road graph and spatial demand layers.
2. Optimization: solve static and resilience-aware resource-placement problems.
3. Machine learning: produce an Iowa transportation incident-risk demand layer from historical public data.
4. Simulation: stress-test configurations across thousands of modeled incidents and disruption scenarios.
5. Cybersecurity: minimize data collection, bound expensive API operations, validate all inputs, secure depen-
dencies/secrets, and document a Take9-aligned threat model.

1. The central research question
The normal version of a location-allocation problem asks:
Where should a fixed number of resources be placed to maximize coverage or reduce modeled travel time?
GridAid goes further:
Where should those resources be placed so that the network remains effective across several
plausible disruptions, not only under normal conditions?
This creates a measurable difference between two kinds of optimization.
Static optimization
The algorithm optimizes one normal road-and-demand state.
Normal roads
Normal demand
All resources available
↓
Static optimizer
↓
Best normal-condition configuration
Resilience optimization
The algorithm chooses one configuration that is evaluated across multiple scenarios.
Normal
Winter slowdown
Major corridor closure
Resource unavailable
Temporary event demand
Combined stress
↓
Shared site-selection decision
↓
Average + worst-case objective
↓
Resilient configuration
A static optimum may achieve the strongest score on a perfect day but degrade sharply during a disruption. A resilient
configuration can accept a small normal-condition tradeoff in exchange for stronger average and worst-case performance.
That comparison is one of the project’s most important competition visuals.

7. Graph routing
The road network is represented as a weighted directed graphG = (V, E) .
• V: intersections and road endpoints;
• E: traversable road segments;
• edge weight: modeled travel time.
For a road edge:
base_time = length / modeled_speed
A scenario can modify that weight:
scenario_time = base_time × condition_multiplier
A complete closure removes the edge from traversal.
Algorithms
GridAid should implement and understand Dijkstra’s algorithm, then validate results against NetworkX. A* can be
used for targeted point-to-point routing if it improves performance, but the core many-to-many problem benefits from
Dijkstra/multi-source methods and matrix precomputation.
Why the matrix matters
Optimization should not rerun thousands of graph searches inside every solver decision.
The preprocessing stage creates:
T[candidate_site][demand_point] = modeled travel time
For 150 candidates and 2,000 demand points, that is 300,000 numeric values—a practical matrix for fast optimization.
Scenario-specific matrices can be cached:
matrix_normal.npy
matrix_winter.npy
matrix_closure.npy
matrix_event.npy
This design is one of the main reasons the final app can feel fast.
8. Static facility-location optimization
Static optimization establishes the benchmark.
Maximum coverage
Choose exactly p candidate sites to maximize weighted demand reachable within a chosen threshold.
Conceptually:
maximize covered weighted demand
subject to exactly p selected resources
p-median
Choose exactly p sites to minimize population/demand-weighted modeled travel time.
p-center / worst-served analysis
A later experiment can minimize the maximum modeled travel time to any demand point.

Validation
On small problems, brute-force every possible configuration and compare it with OR-Tools. For example:
8 candidates choose 3 = 56 configurations
If the solver does not match brute force, the formulation is wrong.
9. Resilience-aware optimization
This is the signature analytical system.
Let a configurationC be evaluated under scenariosS.
For each scenario:
coverage_s(C)
mean_time_s(C)
p95_time_s(C)
A competition-ready resilience score can combine average and worst-case performance:
resilience_score(C)
= alpha × average_s(coverage_s(C))
+ beta × minimum_s(coverage_s(C))
- gamma × relocation_penalty(C)
The weights must be documented and sensitivity-tested.
A stronger solver formulation shares the same site-selection variables across all scenarios while coverage/assignment
variables vary by scenario. The optimizer therefore findsone configuration that works across the scenario portfolio
rather than finding a different optimum for each scenario.
Competition comparison
The final chart should compare:
Synthetic baseline
Static normal-condition optimum
Resilience-aware optimum
under the same scenarios.
The expected pattern is not that the resilient configuration wins every cell. Instead, it should demonstrate the tradeoff
between peak normal-condition performance and stability under disruption.

10. Machine learning subsystem
Machine learning is part of the application, but it must solve a documented problem and have independent validation.
ML task
The recommended subsystem estimatesrelative transportation incident risk in Iowa using historical public crash
and roadway/traﬀic features.
The result becomes an alternative demand layer.
It does not claim to predict every medical emergency or actual emergency-response need.
Possible unit of prediction
• road segment × month; or
• spatial cell × month.
Potential features
• AADT / traﬀic volume;
• truck AADT;
• road class;
• speed limit;
• segment length;
• intersection density;
• urban/rural indicator;
• historical lagged crash frequency;
• season/month;
• surface or weather categories where correctly aligned;
• work-zone indicator.
Target options
• future crash count;
• severity-weighted future crash count;
• binary/ordinal high-risk class.
Models
The project should compare at least:
1. naive historical baseline;
2. simple statistical/linear baseline;
3. tree ensemble such as Random Forest or HistGradientBoosting.
The final model is the one that performs credibly and is explainable—not necessarily the most complex.
Evaluation
Prefer a time-based or grouped split rather than a random row split that leaks geography/time.
Regression metrics:
• MAE;
• RMSE;
• rank correlation if risk ordering matters.
Classification metrics:
• precision/recall;
• PR-AUC;

11. How ML affects optimization
GridAid should let users compare demand assumptions.
Population
w_i = population_i
ML incident risk
w_i = normalized predicted risk_i
Blended
w_i = lambda × normalized_population_i
+ (1-lambda) × normalized_risk_i
The result is not “AI chooses the resource locations.”
Instead:
ML estimates one demand signal
Optimization uses that signal mathematically
Simulation evaluates the resulting placement
That distinction makes the technical architecture more defensible.

13. Monte Carlo validation
The simulation system evaluates configurations across many synthetic incidents rather than one convenient example.
A demand layer becomes a probability distribution:
probability_i = weight_i / SUM(weights)
Sample 10,000+ incidents with a fixed oﬀicial-demo seed.
For each configuration, report:
• mean;
• median;
• p90;
• p95;
• percent within threshold;
• worst scenario;
• average scenario coverage;
• minimum scenario coverage.
The final app should display distributions rather than only a single average.
14. Robustness and sensitivity
The project should test whether its recommendation is stable.
Vary:
• resource count;
• coverage threshold;
• winter multiplier;
• disrupted corridor;
• resource availability;
• population-vs-ML demand blend;
• average-vs-worst-case resilience weight.
Site stability
For each site:
stability = scenarios_selected / scenarios_tested
A site that appears across most reasonable assumptions is more robust than a location selected only by one narrow
model.

The Take9 pledge should be reflected in architecture rather than added only to the submission form.
The public GridAid demo should intentionally collect almost no user data.
Data minimization
Do not collect:
• names;
• emails;
• passwords;
• medical information;
• patient information;
• live 911 records;
• private volunteer home addresses;
• precise user location;
• arbitrary uploaded files.
The app does not need that information to demonstrate its purpose.
Threat model
Assets to protect:
• result integrity;
• API availability;
• model/data artifact integrity;
• deployment secrets;
• trust in public-data timestamps/provenance.
Main threats:
1. expensive optimization requests used for denial of service;
2. malformed inputs designed to crash or exhaust the backend;
3. vulnerable dependencies;
4. secrets accidentally committed to Git or frontend bundles;
5. malformed/compromised third-party feed data;
6. XSS or insecure browser configuration;
7. overly broad CORS;
8. arbitrary model/pickle loading;
9. stale data presented as current;
10. future feature creep that begins collecting sensitive data.

29. Judge-facing technical explanation
A one-minute technical explanation should be memorized:
“I represent the road network as a weighted graph and snap candidate resource sites and demand points
to that graph. I precompute candidate-to-demand travel-time matrices so optimization is fast. The static
modelusesfacility-locationoptimizationtomaximizecoverageorreduceweightedtraveltime. Theresilience
model shares the same selected locations across several disruption scenarios and rewards both average and
worst-case performance. Separately, I train an Iowa transportation incident-risk model on historical public
data and use its output as another demand layer. Finally, I validate configurations with Monte Carlo
simulation and independently test the routing, optimizer and ML model.”

31. Submission-answer drafts
Purpose
GridAidisaresilienceplanningsimulatorthatusesroad-networkalgorithms, optimization, machinelearning
and simulation to test where limited emergency resources can be placed so coverage remains effective when
roads, demand or resource availability change.
Inspiration
I wanted to build an Iowa-rooted project around a real technical problem rather than a stereotypical theme.
Iowa’s rural geography, winter road conditions, public transportation data and technology-supported first-
response initiatives made me interested in a deeper question: a resource layout can look optimal on a normal
day but fail during a disruption. GridAid is designed to measure and optimize that resilience.
Technical challenge
The final answer should use a challenge actually encountered. Strong candidates include:
• generating many-to-many road travel times fast enough for interactive optimization;
• constructing one resource configuration across multiple scenario matrices;
• preventing data leakage in the ML training set;
• correctly invalidating route/matrix caches after a disruption.
Learning
I learned that advanced data science is not just training a model. I had to define honest targets, prevent
data leakage, validate graph and optimization algorithms independently, measure sensitivity to assumptions,
and design the public API so computational features could not be abused.
Version 2.0
A future version would use professionally validated emergency-demand data, expand to more regions and
hazard types, partner with planning professionals, improve robust optimization, and undergo formal security
and operational review before any real-world decision use.
